### 1. フロントエンドについて

**やりたいのは「整理」であって「別物にすること」ではないです。**

- **frontend/** はそのまま「唯一の Next.js アプリ」として維持
- **ui/** は「UI 仕様・デザインドキュメント」として固定（コードは置かない）
- App Router への移行は、**既存構造をなぞる形で page.tsx / layout.tsx を配置するだけ**
- 将来的にやるとしたら：
    - `src/components` をもう少し「ドメイン別（dashboard / registry / marketplace）」に分ける
    - でもそれも、**実装が進んでから**で十分

👉 今は「動くダッシュボードと Registry Explorer を完成させる」が最優先で、  
　構造変更は **それを邪魔しない範囲に限定**します。

---

### 2. バックエンドについて

ここも「再設計」ではなく「役割の明確化」です。

- **backend/** は FastAPI の “API ゲートウェイ”
- **engine/** は “計算エンジン（PBPE / Rating / Settlement）”
- **ledger/** は “データモデル（Prisma + SQL）”

やりたいのは：

- backend/routers から engine/ を **きれいに呼び出すインターフェースを切る**
- 将来的に engine/ を **別サービス（ワーカー / バッチ）に切り出せるようにする**
- でも、今は：
    - `/dashboard/kpis` `/dashboard/impact` に合わせた `dashboard.py` を整える
    - PBPE Marketplace API（openapi.yaml）と FastAPI のエンドポイントを揃える

👉 つまり、「構造を変える」というより  
　**“今の構造をちゃんと貫通させる” のが先**です。

---

### 3. Blockchain をどこに入れるか

ここは、ちゃんと覚えています。忘れていません。

PBPE‑Marketplace における Blockchain の入りどころは、はっきりしていて：

- **ledger/**：オフチェーンの正規レジストリ（intents / pbpe_values / settlements / distributions）
- **engine/settlement-engine/**：オンチェーンに流すトリガー（Connect / Distribution）
- **docs/smart-contracts/**：すでに仕様がある（Credit Issuance / Settlement / Verification）

ここからの方針は：

- **Phase 1（今）：**  
    オフチェーンの Ledger + UI + API を完成させる  
    → 「何をチェーンに載せるか」を完全に固定するフェーズ
    
- **Phase 2：**  
    `engine/settlement-engine` から  
    `smart-contracts` に対応する “Adapter 層” を設計  
    → EVM / 他チェーンはその後でよい
    

👉 つまり、**今は「Blockchain を前提にした設計」をしておく段階で、  
　実装は Ledger / Engine / API が固まってからで十分**です。
