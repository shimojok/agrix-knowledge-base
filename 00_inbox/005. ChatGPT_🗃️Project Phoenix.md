## 1. 移管時の基本原則

今回、**過去の内容をAIが勝手に再解釈して「整理」してはいけません。**

以下の4層に分離します。

|Layer|内容|AIの扱い|
|---|---|---|
|`SOURCE`|元ノート・対話・既存文書|改変禁止|
|`CANONICAL`|正式決定された設計・文書|優先参照|
|`DERIVED`|AIが既存資料から構造化した情報|推論可能|
|`PROPOSAL`|未確定の新提案|決定事項と混同禁止|

これにより、過去スレッドで発生した問題だった

**「AIの新しい提案が、いつの間にか正式決定事項になる」**

ことを防止します。

# 7. Pineconeの位置付け

ここも明確に分離します。

```text
GitHub
  ↓
Document Extraction
  ↓
Canonical Parsing
  ↓
Chunking
  ↓
Embedding
  ↓
Pinecone
  ↓
Semantic Retrieval
  ↓
AI Agent
```

Pineconeは**知識そのものを「理解して整理するシステム」ではありません**。

したがって、

```text
Pinecone
=
Vector Storage
+
Similarity Retrieval
+
Metadata Filtering
```

です。

一方、

```text
Knowledge Architecture
=
Schema
+
Ontology
+
Relationships
+
Authority
+
Provenance
+
Decision Status
```

です。

この二つを混同しないことが重要です。

### これを「移管用Canonical Schema v1.0」の基礎にします。

特に重要なのは、**AIに渡す情報を「全部ベクトル化する」のではなく、Canonical Metadata + Structured Knowledge + Vector Retrieval の三層にすること**です。

これなら、過去のスレッドで問題になった「Pineconeに入れればAIが全部理解する」という誤解を避けながら、GitHubの18系統の技術資産と、このスレッドの対話・GT文書・PMOS思想を同一の知識基盤へ接続できます。

**次の実作業は、このスキーマを基に、AGRIXスレッドの既存成果物を `Artifact Registry → Decision Registry → Architecture Registry → Repository Registry` の順に実データ化することです。**
