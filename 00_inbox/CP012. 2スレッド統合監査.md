# PBPE Marketplace Unified Audit

## 1. Executive Summary（全体要約）

本監査は、PBPE Marketplaceプロジェクトの再構築に向けた統治仕様書の策定を目的とし、PBPE-Marketplace構築スレッドとHealthBook-MI構築スレッドの分析結果を統合しました。

**核心的所見：**

1. **ルーティング構造の二重化**：Pages Router（`pages/`）とApp Router（`app/`）が混在し、コードの重複とパス解決の不整合を引き起こしています。現在の主要実装はApp Routerに移行済みですが、Pages Routerの残骸がプロジェクトの健全性を損なっています。

2. **エンジン統合の未完了**：MBT55・AGRIX・Scope3・HealthBook・PBPE・Registryの6エンジンは個別に実装済みですが、**統合データフローが確立されておらず**、ダッシュボードへの反映が「ダミーデータ」または「部分的なエンジン出力」に留まっています。

3. **設計思想と実装の乖離**：PM046で定義された「完成形UI」と実際の実装の間に、コンポーネント構造・データ連携・インタラクションの点でギャップが存在します。特に、MBT55 ON/OFFは見かけ上の切り替えに留まり、エンジン状態と連動していません。

4. **技術的負債の累積**：Streamlit由来のコード残骸、二重の依存関係、不完全な型定義、環境構築の不安定性（Python 3.14非対応等）がプロジェクトの健全性を損なっています。また、ObsidianノートとGitHub間のドキュメント分散も顕著です。

5. **統治プロセスの欠如**：複数スレッドでの並行開発による仕様のぶれ、AIアシスタントへの過度な依存、変更管理プロセスの不在が、設計と実装の乖離を助長しました。

**結論：** 現状は「プロトタイプ」レベルに留まります。実運用への移行には、App Routerへの完全統一、エンジン統合データフローの確立、レジストリ・ブロックチェーン層の実装を含む体系的なリファクタリングが必要です。


## 2. Original Vision（当初構想）

### 2.1 PM046で定義された完成形UI

PM046は、PBPE Marketplace Dashboard v3の「完成形UI」として以下の6つの画面を定義しました：

| ルート | 画面名 | 主要コンテンツ |
|---|---|---|
| `/dashboard/kpis` | Global KPIs | 6KPIカード（GHG・土壌・水・健康・安定性・PBPE）、発行量ドーナツ、Global Flywheel |
| `/dashboard/impact` | Impact Breakdown | GHG積み上げ棒グラフ（カテゴリ別）、土壌・水・健康指標、改善効果 |
| `/dashboard/market` | PBPE Credits Market | 動的価格モデル、クレジットテーブル、価格履歴ライン |
| `/dashboard/finance` | Bonds & Insurance | Bond価格シミュレーター、フロア可視化、保険商品 |
| `/dashboard/enterprise` | Scope3 × PBPE | 自動変換結果、カテゴリ別内訳、企業ポートフォリオ |
| `/dashboard/pbpe` | PBPE Issuance | 年度別発行量、コンポーネント内訳、Registry（将来拡張） |

### 2.2 統合アーキテクチャのビジョン

AGRIX / HealthBook / MBT55 / PBPE Finance / Scope3 Integrationを「ひとつのUIに統合する」ことが最終目標でした。具体的には：
- **7桁コード（PBPE Identifier Engine）** が全レイヤーを貫く識別子として機能
- **Registry（Layer 5）** が二重計上防止・監査・トレーサビリティの中枢を担う
- **ブロックチェーン（Layer 0）** が改ざん不可の基盤を提供
- **ダッシュボード** がこれらすべてを可視化する「Planetary Value View」として設計

### 2.3 HealthBook-MI設計思想との統合構想

HealthBook-MIは「個人の代謝OS」として、アセチルCoA・エストロボローム・MBT55を中核に据えた統合モデルを志向していました。これはPBPE Marketplace内のHealthBookエンジンと接続され、Health PBPEの計算基盤となるべきものでした。

## 5. Router Strategy（ルーティング戦略）

### 5.1 評価

| 評価軸 | Pages Router | App Router |
|---|---|---|
| Next.js公式推奨 | 旧世代（非推奨） | 最新（推奨） |
| プロジェクトの実態 | 残存コードあり | 主要な6画面が実装済み |
| 将来的な拡張性 | 制限あり | 高い（Server/Client Component分割可能） |
| 学習コスト | 低い（既知） | 中程度（新規習得要） |
| 開発効率 | 既存資産活用可能 | 新規実装が必要 |

### 5.2 判定：**App Routerへ完全統一**

**理由：**

1. **プロジェクトの実態がApp Routerに移行済み**：6画面すべてが`app/dashboard/`に実装済みであり、`pages/`は不要な残存コードです。
2. **Next.js公式の将来性**：App RouterがNext.jsの標準であり、Pages Routerは将来的にサポートが縮小されます。
3. **エンジン統合との親和性**：App RouterのServer Componentはバックエンドデータとの連携に適しており、エンジン統合後のデータフェッチが効率的に行えます。
4. **保守性**：二重構造を解消することで、コードベースが単純化され、保守性が向上します。

### 5.3 移行方針

1. `frontend/pages/` ディレクトリを完全に削除
2. `frontend/src/` 内の不要コードを削除（Streamlit/旧Reactの残骸）
3. `frontend/app/` を唯一のルーティング構造として確立
4. 必要に応じて`frontend/components/` に共通コンポーネントを切り出す
