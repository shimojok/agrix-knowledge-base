BioNexus-Knowledge-Base の資産のまま売却する訳ではありません。ここから何を生み出せるか？このような市場を創出出来るかと言う確信を見せるのです。世界が見落としてきたハイパーサイクル、バイオセキュリティ機能などと、それらによるPBPE金融モデルの価値を、アーキテクチャ構築やシミュレーションシステムにより提案するのです。

そのためにも、AIのハルシネーションとメモリ異常を完全防止するために、生Vault データの整備、RAG/ベクトルデータベース化、MCPなどの構築インフラ整備を最優先します。
また、AI間の正確な情報伝達のために「AI統合指示書」を掲載するGitHub掲示板（Discussions）の導入、自然言語だけでなく、AIが認識しやすいコードやデータベースなどを多用します。

さらに、
AIがAPI を呼び出し、
PBPE Simulator → API → 最新データ → KB更新 → Dashboard更新
などの完全自動のシミュレーションループが成立する機能の導入も検討してください。

---

了解しました。「資産の売却」ではなく「市場創出の確信を示す実証」という位置づけなら、**動くデモンストレーション(実測で校正したループ1本)**が最強の提案材料になります。優先順位も妥当です。3点だけ設計上の修正をお勧めします。

## 1. 「完全防止」ではなく「多層防御」

ハルシネーションとメモリ異常は完全にはゼロにできません。**起きても検知・遮断できる設計**にするのが現実的です。

- **生Vaultは不変(読み取り専用)**：整備は派生層で行い、元データは変更しません(contract-first)。
- **全回答に引用必須**：根拠チャンクのIDがない主張は出力しない。
- **証拠グレードで検索を制御**：`simulated`/`hypothesis` を `measured` として引用させない。
- **整合性検査**：物質収支の不成立、出典なしノード、重複・矛盾を自動チェック。
- **評価セット**：既知の正解質問50〜100問を作り、RAG更新のたびに回帰テスト。

## 2. AI統合指示書とGitHub Discussions

- **正本はリポジトリ内のファイル**(例：`AI_INSTRUCTIONS.md` と、機械可読な `schema/*.yaml`、`contracts/*.json`)に置き、バージョン管理します。
- **Discussionsは告知・Q&A・変更提案の場**とします。編集や削除ができ、版管理も弱いため、正本には向きません。
- **公開範囲に注意**：公開リポジトリのDiscussionsは誰でも読めます。`disclosure_level` が `internal_only`/`partner_nda` の内容、メカニズム、APIキーは載せないでください。非公開リポジトリの利用も検討を。
- 指示書は自然言語を最小限にし、**スキーマ・禁止事項・入出力例をコードとJSONで記述**するとAI間の解釈のぶれが減ります。

## 3. 自動シミュレーションループ

構成案：
`PBPE Simulator → API → 最新データ取得 → 検証ゲート → KB更新 → Dashboard更新`

特に重要な安全設計が3点あります。

- **循環汚染の防止**：シミュレーション出力をKBに戻すとき、必ず `simulated` グレードで保存し、実測として再利用させません。そうしないと、AIが自分の推計を証拠として学習し続けます。
- **検証ゲート**：スキーマ検証・収支検査・異常値検知を通過した更新だけを反映し、失敗時は隔離キューに送ります。
- **人の承認と巻き戻し**：KB更新はバージョン管理(Git/スナップショット)し、金融値(クレジット量など)の外部公開前には人の承認を挟みます。

## 提案する着手順

1. 生Vaultの棚卸しと、frontmatter付与(試験的に20ノート)
2. ベクトルDB＋引用必須RAG＋評価セット
3. MCPサーバー(KB検索、スキーマ検証、シミュレーター呼び出し)
4. 1シナリオ限定のループ(例：ケニアの圃場1か所で実測 → PBPE推計)

実測値で校正した1ループがあれば、提案の説得力が大きく変わります。次は、**インフラ全体の構成図とMCPツール仕様(入出力定義)**を作りましょうか。
