了解しました。
既に、生Vault の整理を進めていますが、必要なメタデータの項目を教えて下さい。
但し 整理しても6,000ものノートとなるため、デイリーノートへのメタデータ付与は可能ですが、全てのノートへの付与は不可能です。
また、6,000ものノートには、GitHub実装のやり取り記録があちますが、それらは削除すべきでしょうか？

---

結論から申し上げます。6,000件すべてのノートに手作業でメタデータを付与する必要はありません。また、GitHub実装のやり取り記録も、原則として削除しないでください。

BioNexus-Knowledge-Baseでは、メタデータを付ける対象を階層化します。Daily Notesを時系列の索引として活用し、個々のノートは既存情報をできる限り利用して機械的に分類します。重要な設計原則は、原本を保全し、必要な情報を検索・追跡できるようにすることです。

## 1. メタデータ設計：3階層に分ける

第1階層：Daily Notes — 必須

手作業で管理する中心

日付、主要プロジェクト、関連プロジェクト、議題、関連ノートへのリンク、決定事項・未解決事項を管理します。既存のDaily Noteを時系列インデックスとして利用します。

第2階層：通常ノート — 最小限

既存情報から自動取得

全件への手作業は行いません。ファイルパス、ファイル名、見出し、リンク、既存frontmatter、Git履歴などから、プロジェクト・文書種別・日付を可能な範囲で自動推定します。推定結果は確定情報と区別します。

第3階層：重要な正式成果物 — 詳細管理

アーキテクチャ、データスキーマ、正式決定、Evidence Registry、金融モデル、API仕様など、将来のAI実装やMicrosoftへの移管に直接影響する文書には、出典・バージョン・状態・検証情報を付与します。

## 2. Daily Noteに付与するメタデータ

Daily Noteは、6,000件の知識資産を横断するための時系列インデックスにします。以下を標準案とします。

| 項目                 | 必須 | 用途                        |
| ------------------ | -- | ------------------------- |
| `date`             | 必須 | 記録日                       |
| `primary_project`  | 必須 | 主担当プロジェクト                 |
| `related_projects` | 必須 | 関連プロジェクト。なければ空配列          |
| `domains`          | 必須 | 科学、農業、健康、金融、AI基盤など        |
| `topics`           | 推奨 | 具体的な議題・研究テーマ              |
| `record_type`      | 必須 | 議論、決定、実装、検証、課題など          |
| `status`           | 必須 | 草案、検討中、確定、保留、廃止など         |
| `source_refs`      | 必須 | 根拠となるノート、コード、GitHub記録への参照 |
| `decision_refs`    | 推奨 | 正式決定に関連する記録               |
| `next_actions`     | 推奨 | 未完了の作業                    |
| `tags`             | 推奨 | 横断検索用のタグ                  |

### YAML記述例

YAML

```
---
date: 2026-10-14
primary_project: PBPE
related_projects:
  - AGRIX
  - MBT55-MSC
domains:
  - finance
  - data-science
topics:
  - impact-asset-architecture
  - simulator-api
record_type: implementation_discussion
status: in_progress
source_refs:
  - "[[PBPE Simulator API設計]]"
decision_refs: []
next_actions:
  - API仕様の確定
tags:
  - bionexus
  - provenance
---
```

これは記述形式の例であり、実際のDaily Noteの内容を示すものではありません。

### 運用上の注意

* `primary_project` は固定した6プロジェクトの名称を使います。

* `related_projects` は複数指定できます。

* `status` は「文書の状態」を表し、科学的証拠の確度とは分離します。

* `source_refs` は可能な限り実在するノートや成果物へのリンクにします。

* 日付がファイル名から取得できる場合は自動取得し、本文の日付と異なる場合は無断で上書きせず差異を記録します。

## 3. 通常ノートには何を付けるべきか

全ノートに大量のYAMLを手入力する必要はありません。通常ノートの管理情報は、ファイル外部のインデックスDBでも保持できます。

| 項目                 | 取得方法            | 位置づけ             |
| ------------------ | --------------- | ---------------- |
| `source_id`        | 自動採番            | 必須               |
| `file_path`        | ファイルシステムから取得    | 必須               |
| `title`            | ファイル名・見出しから取得   | 必須               |
| `file_hash`        | ファイル内容から計算      | 必須               |
| `modified_at`      | ファイル情報から取得      | 必須。ただし内容の作成日とは区別 |
| `primary_project`  | フォルダ・リンク・内容から推定 | 不明なら未分類          |
| `document_type`    | ルール・分類器で推定      | 不明なら未分類          |
| `source_date`      | 本文・Git履歴等から取得   | 確認できる場合のみ        |
| `evidence_status`  | 証拠管理ルールに基づいて付与  | 重要文書から優先         |
| `canonical_status` | 正式決定台帳と照合       | 自動的な確定は禁止        |

`file_hash` は、同一内容の検出や変更追跡に役立ちます。ただし、ハッシュが同じでも保存場所や由来が異なることがあるため、検証前に原本を削除してはいけません。

また、`evidence_status` と `canonical_status` は別項目です。例えば、実験結果の記録が存在することと、その結果が正式なアーキテクチャとして採用されたことは別の事実です。

## 4. GitHub実装のやり取り記録は削除すべきか

原則として保存します。削除ではなく、分類・関連付け・アーカイブを行います。

GitHub実装のやり取り記録には、完成したコードだけでは分からない重要情報が含まれます。

* なぜ現在の設計が選ばれたのか

* どの実装が失敗し、何が修正されたのか

* AIがどの仕様を誤認し、どの指示で修正されたのか

* API、スキーマ、リポジトリ構造がいつ変更されたのか

* どの提案が採用され、どの提案が却下されたのか

これらは、AIの過去の誤りを繰り返さないための重要な履歴です。ただし、過去の会話をすべて現行仕様としてRAGに同じ優先度で検索させると、古い情報が混入する危険があります。

### 推奨する4分類

A. 正式な実装成果物

現行コード、確定済みAPI、スキーマ、テスト、リリース記録。現行仕様と対応するバージョンを明示します。

B. 意思決定・変更履歴

設計の理由、修正理由、採用・却下の経緯。Daily Noteや正式決定記録から参照できるようにします。

C. 旧仕様・失敗した実装・重複記録

原本は履歴として保管し、`superseded`、`failed`、`duplicate_candidate` などの状態を付与します。検索時には現行仕様と区別します。

D. 除去・隔離が必要な記録

APIキーや認証情報などの秘密情報、明確な機密情報、不要な個人情報は適切に隔離・除去します。秘密情報がGit履歴に含まれる場合は、現行ファイルから削除するだけでなく、認証情報の失効・再発行と履歴への対応も検討します。

削除を検討するのは、重複が確認され、参照関係と保存要件を検査した後などに限定します。「古い」「AIの会話である」「完成版ではない」という理由だけでは削除しません。

## 5. これからの作業順序

1. Daily Noteの既存メタデータを確認し、必要な項目だけを追加する。

2. 約6,000件を走査し、ファイルパス・ハッシュ・リンク・既存メタデータを外部インデックスへ登録する。

3. GitHub実装記録をA〜Dに分類する。最初は自動判定結果を確認対象として出し、削除は行わない。

4. 重要な正式成果物から、出典・証拠状態・正式決定との関係を整備する。

5. その後にRAG・ベクトルDBを構築し、現行仕様と過去の議論を区別して検索できるようにする。

まずは、全ノートへの手作業によるメタデータ付与を作業要件から外し、Daily Note＋自動生成インデックス＋重要成果物の詳細管理という方式で進めるのが適切です。これなら、既存Vaultの整理作業を止めずに、将来のRAG・MCP・自動シミュレーションへ接続できます。
