## フェーズ0：ローカルRAG再構築（着手中・最優先）

現状 agrix-knowledge-base は4,900+ノート中3,400+処理済み、Pinecone（llama-text-embed-v2）へのアップロード中です。ここでの「再構築」は、単にアップロードを完走させることではなく、**kb016の訂正を反映した検索優先度**を持たせることです。

- 完了判定：`03_MBT55`・`04_AGRIX`・`06_PBPE`・`02_Biological_Systems`・`05_AgriWare` への検索クエリで、γ_ij・CCE・HFR・NCS・Wilkinson由来の一次情報が上位ヒットすることを `scripts/ask_rag.py` で疎通検証済み
- `07_HealthBook` は検索対象に含めるが、優先度を下げるメタデータタグ（`domain: healthbook`, `priority: deferred`）を各ノートに付与し、誤って主要ソースとして引かれないようにする
- ここが崩れると、以降どのフェーズで生成されるコードも「HealthBookの例え」に引きずられる、前回自分がやった間違いがそのまま再発します

## フェーズ1：16リポジトリのRAG化

`/areas/repo-consolidation.md` にある統合方針（M3-BioSynergy→M3-Core-Engine、HealthBook-AI→HealthBook-MBT55-Unified、PBPE群→PBPE-Marketplace、Azure-PMOS→BioNexus-Enterprise）を先に実行してから、統合後のリポジトリをRAG化する順序を推奨します。先にコードをRAG化してから統合すると、統合で消えるはずの重複コードまでインデックスに残り、検索汚染になります。

- 統合後の各リポジトリについて、README／docstring／関数シグネチャを抽出し、Obsidianノートと同じPineconeインデックス（別namespace: `agrix-code-base` など）に格納
- ノート（理論）とコード（実装）を分離したnamespaceにしておくことで、後述のコード生成AIが「理論ノートを参照して型安全なコードを書く」「既存コードを参照して重複実装を避ける」を両方できるようにする

## フェーズ2：Python Hypercycle Schemeの枠組み確定

前回訂正した `core/` → `mbt_hypercycle/` → `agrix/`（`healthbook/`は凍結）の骨格を、**コードではなく仕様として先に固定**します。ここでPydanticスキーマとインターフェース（`BaseHypercycleEngine`）だけを確定し、中身の実装は次フェーズ以降に回す。枠組みを先に固定する理由は、フェーズ3以降で生成AIにコードを書かせる際、AIが毎回違う抽象を作ってしまうのを防ぐためです。

## フェーズ3：コードを扱う生成AI

ここが最も設計判断が要る箇所です。役割を厳密に絞ってください——**生成AIは「フェーズ0/1のRAGから抽出した仕様を、フェーズ2で固定した型に流し込む」だけの変換器**とし、数値や生化学ロジックそのものは考案させない。

- 入力：RAG検索結果（ノート＋既存コード）＋ フェーズ2のPydanticインターフェース
- 出力：そのインターフェースを満たす `.py` ファイル（ドラフト）
- 人間（Kazさん）のレビュー必須ゲート：$\gamma_{ij}$ のような実測値ベースの数式は、生成AIの出力をそのまま採用せず、RAGの一次ソース（ノートの数式）と1行ずつ突合してから確定
- ここで Claude Code のような、ファイル操作とRAG検索を両方エージェント的に行えるツールを使うと、「ノート検索→コード生成→既存コードとの整合チェック」を1セッションで回せます

## フェーズ4：生成されるJSONコードの格納

kb005で定義済みの `agrix-platform-kb.json` / `healthbook-platform-kb.json` の出力先を、単一ディレクトリではなくスキーマバージョン管理付きで設計します。

```
outputs/
├── agrix-platform-kb/
│   ├── schema_v1/
│   └── schema_v2/
└── healthbook-platform-kb/   # 凍結中は空のまま
```

各JSONに、前回提案した「来歴バーコード」（由来ノートID＋入力ハッシュ＋エンジンバージョン）を必須フィールドとして持たせておくと、フェーズ5の抽出コードが「この数値はどのノートのどの数式から出たか」を自動で追跡できます。

## フェーズ5：JSONから必要情報を抽出するPython Code

フェーズ4のJSON群を読み、用途別（IPCC提出用、投資家向けダッシュボード、PBPE Marketplace取引用など）に整形するレイヤーです。ここは決定論的な集計・変換のみで、生成AIを関与させない方が安全です（数値の二次加工にAIを挟むと、来歴バーコードの意味が薄れる）。

## フェーズ6：必要なツール・ライブラリの整理

現時点で判明している要件から逆算すると、最低限これだけは先に固定しておくべきです。

|用途|候補|
|---|---|
|RAG検索|ChromaDB（ローカル）or Pinecone（既存）|
|型安全スキーマ|Pydantic v2|
|動的平衡モデル|NumPy / SciPy（`solve_ivp`）、勾配が要る場合はJAX|
|コード生成エージェント|Claude Code（ファイル操作＋RAG検索を1エージェントで）|
|JSONバージョン管理|Pydanticの`model_json_schema()`によるスキーマ自体の出力・差分管理|
|来歴追跡|ハッシュはstdlibの`hashlib`で十分、外部依存を増やさない|

ライブラリはここで確定させ、フェーズ7以降で追加するのは基本的に避ける方針が、work-preferences にある「作業の同時並行を避ける」「完璧より動くコード」と整合します。

## 全体フロー：AGRIX Knowledge Base System (BioNexus Engine)

上記7フェーズを積み上げた結果としての全体像です。

```
[Obsidian Vault: agrix-knowledge-base]
    │ (Phase 0: 埋め込み・優先度タグ付け)
    ▼
[Pinecone RAG Index] ⇄ [16 Repos RAG Index]        ← Phase 0-1
    │
    ▼
[Python Hypercycle Scheme: core/ → mbt_hypercycle/ → agrix/] ← Phase 2（仕様固定）
    │
    ▼
[コード生成AI: RAG仕様 → Pydantic型準拠コード]      ← Phase 3（人間レビューゲート）
    │
    ▼
[agrix-platform-kb.json（来歴バーコード付き）]      ← Phase 4
    │
    ▼
[抽出・整形Python Code] ─┬→ IPCC提出用レポート
                          ├→ 投資家ダッシュボード（PBPE NPV等）
                          └→ RAGへのフィードバック（新知見の還元・循環完了）
```

**BioNexus Engine** という名称にふさわしいのは、最後の矢印（成果がRAGへ還元される）が実際に機能して初めてです。それまでは単なる一方向のパイプラインであり、ハイパーサイクルではありません。フェーズ4のJSONを新規ノートとしてVaultに書き戻し、フェーズ0のインデックスに再度乗せる仕組みを、どこかのフェーズで明示的に組み込む必要があります——これを後回しにすると、せっかくの「循環」構想が実装上は循環しないまま終わります。
