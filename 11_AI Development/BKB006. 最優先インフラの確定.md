重要なのは、RAGやベクトルデータベースを導入するだけでは不十分だという点です。RAGは誤った情報も検索できますし、AIのメモリ異常も単独では防げません。したがって、原本・出典・確定状態を管理する仕組み、AIが参照する仕組み、APIで実行する仕組み、結果を検証して反映する仕組みを一体化します。

## 1. 最優先インフラの確定

P0 — 生Vaultの整備と原本保全

約6,000件のObsidianノートとDaily Notesを対象に、原本・ファイルID・更新履歴・内部リンク・日付・所属プロジェクトを保持する。重複、欠落、リンク切れ、文字コード、メタデータの問題を検査する。

P1 — 出典・決定状態・変更履歴の標準化

原本、AI生成案、仮説、観測データ、検証済み証拠、正式決定を区別する。AIの過去の回答を自動的に正解として扱わない。

P2 — ローカルRAG・ベクトルDB・構造化KB

原文チャンク、文書ID、位置情報、日付、プロジェクト、証拠状態、バージョンを関連付ける。ベクトル検索に加えて、キーワード検索と構造化データ検索を併用する。

P3 — MCP・API・権限管理

AIエージェントが許可されたデータを読み取り、定義済みのAPIを実行できるようにする。読み取り・計算・KB更新・公開の権限を分離し、認証、監査ログ、失敗時の停止条件を設ける。

P4 — GitHub DiscussionsとAI統合指示書

AI間の共通指示、変更通知、設計上の論点を共有する。Discussionの投稿だけを正式仕様にせず、確定した指示・スキーマ・設定はGitHubリポジトリ内の版管理された機械可読ファイルに反映する。

P5 — PBPE Simulatorの自動連携

Simulator、API、最新データ、検証、KB更新、Dashboard更新を接続する。ただし、データ検証や承認条件を通過しない結果は正式データとして公開しない。

これらは、既存の10領域のデータサイエンス構想に追加する共通基盤レイヤーです。個々の研究・金融モデルより先に、この基盤の整備を進めます。

## 2. PBPE Simulatorの完全自動ループ

この機能は実現可能です。ただし、シミュレーション結果を自動生成することと、検証前の結果を自動的に正式データとして採用することは明確に分離します。

① PBPE Simulator

シナリオ・パラメータ・モデルバージョン

② API / MCP Gateway

認証・権限・入力検証・実行ID発行

③ 最新データの取得とスナップショット化

出典・取得時刻・単位・データ品質・バージョン

④ 計算・再現性・品質検証

スキーマ検証、異常値検知、NPV・IRR・回帰テスト

⑤ 検証済みステージング

差分確認・承認条件・失敗時のロールバック

⑥ Knowledge Base

構造化データ・Evidence Registry・RAG索引を更新

⑦ Dashboard

検証済み結果・実行履歴・金融KPIを更新

各実行を記録し、次のシミュレーションへ。検証に失敗した場合は公開を停止する。

### 自動化で必須となる制御

* データの鮮度： 最新データを取得できなかった場合、古い値を最新値として扱わない。

* 再現性： 同一の入力スナップショット、モデルバージョン、パラメータから計算を再現できるようにする。

* 二重実行防止： API再試行で同じ更新が重複登録されないよう、実行IDと冪等性キーを使用する。

* 金融モデル検証： NPV、IRR、Green Premium、リスク感応度の計算を回帰テストする。

* 公開制御： 検証済みデータだけを本番KBとDashboardへ反映し、異常時には停止・通知・ロールバックを行う。

* 監査可能性： 誰が、どのAIエージェントを通じて、どのデータとモデルで実行したかを記録する。

なお、完全自動化の対象は、検証条件が明確な処理です。新しい生物学的機序の解釈、証拠の確定、アーキテクチャの変更などは、最初から無条件の自動承認にしません。

## 3. AI統合指示書の形式

GitHub DiscussionsはAI間の協議・通知に使い、確定情報はリポジトリ内の機械可読ファイルに固定します。

| ファイル形式                 | 主な役割                |
| ---------------------- | ------------------- |
| `AGENTS.md` / Markdown | 共通任務、禁止事項、実行規則      |
| YAML                   | エージェント権限、処理フロー、環境設定 |
| JSON Schema            | API入出力、KBレコード、検証ルール |
| JSON / JSONL           | 証拠レコード、実行ログ、構造化知識   |
| SQL / DB migrations    | データベース構造、バージョン変更    |
| OpenAPI                | APIの正式な契約・入出力仕様     |

正式な指示書には、最低限 `instruction_id`、`version`、`status`、`owner`、`effective_date`、`supersedes`、`source_refs` を持たせます。これにより、異なるAIが古い指示や非公式な会話を最新の仕様と誤認するリスクを低減できます。
