# AGRIX Knowledge Base System (BioNexus Engine) 実現の全体的な流れ

> 起点思想: BioNexus Python Hypercycle Scheme（kb005改訂版・MBT55起点）
> 目的: ローカルRAG＋16リポジトリ→Pythonハイパーサイクルエンジン群→JSONナレッジ還流の自律システムを構築する

---

## 0. 全体構造（俯瞰図）

```
[16リポジトリ + agrix-knowledge-base (Obsidian Vault)]
        │ ① RAG化（ingestion）
        ▼
[ローカルRAG基盤 (ChromaDB/LanceDB + 日本語埋め込み)]
        │ ② 検索・根拠抽出（優先フォルダ構造を内蔵）
        ▼
[BioNexus Python Hypercycle Scheme 枠組み (core/)]
        │ ③ ノード規約・パイプライン制御
        ▼
[コード生成AI層] ──④ 生成──► [個別Pythonエンジン群 (agrix/mbt_hypercycle等)]
        │                              │
        │ ⑤ JSONスキーマ契約           │ ⑥ 実行
        ▼                              ▼
[JSON格納層 (agrix-platform-kb.json等)] ◄── 成果
        │ ⑦ 抽出・照会
        ▼
[BioNexus Engine (AGRIX Knowledge Base System)]
        │ ⑧ 新ナレッジとしてRAGへ還流（ループ閉鎖）
        └──────────────────────────────►
```

## Stage 1: ローカルRAGの再構築・16リポジトリのRAG化

### 1.1 目的
全知識ソースを**一つの検索空間**に統合し、「03_MBT55 > 04_AGRIX > 06_PBPE > 02_Biological_Systems > 01/05 > 07_HealthBook(凍結)」の優先構造を検索時に強制する。

### 1.2 作業項目
| # | 作業 | 成果物 |
|---|---|---|
| 1-1 | 16リポジトリ＋Vaultの棚卸し（サイズ・形式・ライセンス） | `inventory.md` |
| 1-2 | 取り込みパイプライン `ingest/`（Markdown/PDF/CSV/code） | `ingest.py` |
| 1-3 | チャンキング規約（数式は単位チャンク保護、frontmatter維持） | `chunking_policy.md` |
| 1-4 | 埋め込みモデル選定・検証（日本語: multilingual-e5-large等、ベンチマークで決定） | `eval/retrieval_eval.py` |
| 1-5 | メタデータ設計（`{repo, folder_priority, note_id, formula_flag}`） | collection schema |
| 1-6 | 疎通検証 `scripts/ask_rag.py`（「栄養カスケードの速度論」「CCE数式」等のクエリで一次情報がヒットするか） | 検証レポート |

### 1.3 受け入れ条件
- 優先度1〜3のフォルダからのヒット精度（Recall@5）が閾値以上
- HealthBook関連クエリが「凍結」扱いであることがメタデータで判別可能

### 1.4 ツール
ChromaDB または LanceDB / sentence-transformers / LlamaIndex or 自前ingester / uv

## Stage 2: Python Hypercycle Scheme の枠組み（core/）

### 2.1 目的
全エンジンが従う**型安全な契約**を先に固定し、以降の個別コードを「差し替え可能な触媒」として扱えるようにする。

### 2.2 作業項目
| # | 作業 | 成果物 |
|---|---|---|
| 2-1 | 基底モデル `core/base_model.py`（HypercycleNodeResult, BaseHypercycleEngine） | core |
| 2-2 | パイプライン `core/pipeline.py`（DAG定義・ノード結合・還流ループ） | core |
| 2-3 | RAGインタフェース `core/rag_interface.py`（優先度フィルタ付き検索API） | core |
| 2-4 | genome外部化 `genome.json`（全係数の集中管理・世代管理） | config |
| 2-5 | テスト基盤（pytest, 決定論性検証: 同入力→同出力） | tests/ |

### 2.3 受け入れ条件
- ダミーノード2個を接続して「事象→JSON」の最小ループが1本動く
- 全数値導出がPydantic v2スキーマを通過する（LLM直接出力の数値を禁ずる）

---

## Stage 3: コードを扱う生成AIの統合

### 3.1 目的
生成AIは**コード記述とRAG根拠の要約に専念**し、数値導出は実行時にPythonが担う。ハルシネーション混入を構造的に防ぐ。

### 3.2 作業項目
| # | 作業 | 成果物 |
|---|---|---|
| 3-1 | エンジン生成用プロンプト規約（必須: Pydantic入出力型、RAG引用ID、係数はgenome参照禁止の直接記述を排す） | `prompts/engine_gen.md` |
| 3-2 | 生成→検証ループ（生成コードを自動でpytest＋型チェック＋RAG根拠突合） | `tools/gen_verify.py` |
| 3-3 | 採用基準（fitness: テスト通過率・根拠一致率・複雑度） | 評価指標定義 |

### 3.3 ルール
- 生成AIが出力してよいもの: Pythonコード、JSONスキーマ案、テストケース
- 生成AIが出力してはいけないもの: 最終数値、係数の確定値（genome経由のみ）

## Stage 6: 個々のPython Codeの作成（エンジン群）

### 6.1 優先順位（RAG優先構造に従う）
```
1. agrix/mbt_hypercycle/   栄養カスケード・γ_ij行列・MHTコア     ← 起点
2. agrix/agrix_phenotype/  土壌・作物代謝・環境応答
3. agrix/pbpe/             CCE/HFR/NCS・炭素クレジット・価値変換
4. agrix/agriware/ + safetychain/  資材施用・トレーサビリティ
─────────────────────────（凍結解除後）
5. healthbook/pathways/    MHT流用: SCFA→ATP・GLP-1
```

### 6.2 各エンジンの開発サイクル（ハイパーサイクル的）
```
RAG根拠抽出 → スキーマ設計 → (生成AIでコード草案) → 検証ループ
→ genome係数登録 → エンジン結合テスト → 採用 → JSON格納 → 還流
```

### 6.3 受け入れ条件（エンジン単位）
- RAG抽出パラメータとの突合レポート付き
- 決定論性テスト・回帰テスト通過
- 上流ノード出力→自ノード入力の結合テスト通過

## Stage 7: AGRIX Knowledge Base System (BioNexus Engine) への統合

### 7.1 統合アーキテクチャ
```
BioNexus Engine
├── RAG層        (Stage 1) — 知識の検索・根拠供給
├── Scheme層     (Stage 2) — ハイパーサイクル制御
├── エンジン層   (Stage 3,6) — 代謝・価値計算の触媒群
├── KBストア層   (Stage 4) — 成果JSONの格納
├── 照会層       (Stage 5) — 抽出・意思決定供給
└── 還流ループ   — 新JSONをチャンク化→RAG再索引（循環完了）
```

### 7.2 最終統合テスト
- シナリオ: 「廃棄物投入量と環境条件を与えると、GHG削減・NCS・PBPE価値がJSONで出力され、
  その内容がRAG検索で再び根拠として引ける」という**一周テスト**を合格させる

### 7.3 運用ルール（絶対遵守の再掲）
- RAG疎通・一次情報精度が保証されるまで HealthBook コードは生成しない
- 数値は常にPython実行由来。生成AIの文章内数値は根拠候補であって確定値ではない

## 付録: 必要なツール・ライブラリ一覧

| 分類 | 候補 |
|---|---|
| ベクトルDB | ChromaDB / LanceDB |
| 埋め込み | sentence-transformers (multilingual-e5 / bge-m3 等、ベンチで選定) |
| 型・スキーマ | Pydantic v2 |
| 数値計算 | numpy, scipy (ODE), pandas |
| ネットワーク | networkx (γ_ij解析) |
| API/実行 | FastAPI, Typer (CLI) |
| 品質 | pytest, ruff, mypy |
| 環境 | uv, Docker |
| 生成AI連携 | ローカルLLM or API（コード生成・要約専用に隔離） |

## ステージ間の依存関係

```
Stage 1 (RAG) ──必須──► Stage 2 (Scheme枠組み) ──► Stage 3 (生成AI) ──► Stage 6 (エンジン群)
                                    │                                        │
                                    └──► Stage 4 (JSON格納) ◄────────────────┘
                                              │
                                              └──► Stage 5 (照会層) ──► Stage 7 (BioNexus Engine統合)
```

Stage 4・5は枠組み確定後に並行開発可能。Stage 7は全ステージの受け入れ条件通過後に統合。
