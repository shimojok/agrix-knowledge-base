# BioNexus Local Knowledge Engine v1.0 — 実装構成案

実装環境：Windows PC／Obsidianと同一PC／RAM 16 GB

この条件では、クラウド型の大規模システムを先に構築するのではなく、Windows上で動作するローカルLLMを中核に、既存Vaultを直接検索できる知識基盤を構築するのが合理的です。

設計原則は3つです。

1. 原文を保全する。 Obsidian Vaultを正本とし、インデックスやデータベースを再生成可能な派生データとして扱う。

2. 必要な情報だけを取得する。 全ノートをLLMに読み込ませず、意味検索・全文検索・リンク探索で対象を絞る。

3. 出典を追跡できる。 検索結果から原文ファイル、見出し、行・段落へ戻れるようにする。

この構成を、BioNexusの知識基盤における実装案 v1.0 として提示します。まだ実装・動作検証済みという意味ではありません。

## 2. Windows上のディレクトリ構成

Vaultの中にデータベースを混在させず、Vaultの外に実行環境とインデックスを配置します。

```
C:\BioNexus\
│
├── config\
│   └── settings.yaml
│
├── engine\
│   ├── scanner.py          # Vault走査
│   ├── parser.py           # Markdown/YAML解析
│   ├── chunker.py          # 見出し単位の分割
│   ├── embedder.py         # Ollama Embedding
│   ├── indexer.py          # インデックス更新
│   ├── retriever.py        # ハイブリッド検索
│   └── provenance.py       # 出典・位置情報
│
├── mcp_server\
│   └── server.py           # MCPツール公開
│
├── data\
│   ├── bionexus.sqlite3    # Source DB・全文検索
│   └── chroma\             # Vector DB
│
├── logs\
└── tests\
```

`settings.yaml` には実際のVaultパスを設定します。上記は推奨配置であり、既存のVaultを移動・改変する必要はありません。

## 3. 各処理の仕様

| 処理        | 実装仕様                                                 |
| --------- | ---------------------------------------------------- |
| ノート解析     | Markdown、YAML frontmatter、Obsidian Wiki Links、見出しを解析 |
| ノート識別     | 正規化した相対パス、内容ハッシュ、更新日時を記録                             |
| チャンク分割    | 見出し・段落を優先し、長文だけ分割。初期目安は500〜800トークン、重複80〜120トークン      |
| Embedding | Ollamaの `bge-m3` で生成                                 |
| 意味検索      | Chromaで類似チャンクを検索                                     |
| キーワード検索   | SQLite FTS5で固有名詞・コード・識別子を検索                          |
| 検索統合      | 意味検索と全文検索を統合し、重複排除・順位調整                              |
| 出典管理      | ファイルパス、見出し、チャンクID、原文ハッシュを返す                          |
| 更新処理      | 変更ファイルのみ再解析・再インデックス化                                 |
| リンク探索     | Wiki Links、バックリンク、関連ノートを取得                           |

特にBioNexusでは、`MBT55`、`AGRIX`、`PBPE`、`MIOS` などの固有識別子が重要です。意味検索だけに頼らず、意味検索＋キーワード検索＋リンク探索の3方式を併用します。

## 4. MCPがLLMに公開する機能

初期バージョンでは、次の5つに限定します。

search_notes

質問・キーワードに関連するノートと該当箇所を検索する。

read_note_section

指定ノートの特定見出しや範囲を取得する。

get_related_notes

Wiki Links・バックリンクから関連ノートを探索する。

get_source_metadata

出典、ファイルパス、更新日時、ハッシュなどを取得する。

get_index_status

最終インデックス日時、登録件数、未処理ファイルを確認する。

各検索結果には、少なくとも以下を含めます。

* `source_id`

* `relative_path`

* `heading`

* `matched_text`

* `content_hash`

* `relevance_score`

これにより、LLMが生成した説明と、実際の原文・出典を区別できます。原文を引用する際も、元ノートに戻って検証できます。

## 5. 実装順序

1. Phase 1 — ローカル実行環境

   Ollamaをインストールし、`qwen3:4b` と `bge-m3` を取得。LLMの応答とEmbedding生成をそれぞれ確認します。

   `powershell ollama pull qwen3:4b ollama pull bge-m3 ollama run qwen3:4b`

2. Phase 2 — Source DB

   Vaultを読み取り専用で走査し、ノート一覧・メタデータ・リンク情報をSQLiteに登録します。原文の保存場所は変えません。

3. Phase 3 — Vector DB

   ノートをチャンク化してEmbeddingを生成し、Chromaに保存。更新検知と再インデックス化を実装します。

4. Phase 4 — 検索エンジン

   全文検索、意味検索、リンク探索を統合し、検索結果の出典追跡を検証します。

5. Phase 5 — MCP Server

   5つの検索・参照ツールを実装し、MCP Inspectorなどの対応クライアントで動作テストします。

   ![](https://www.google.com/s2/favicons?domain=https://py.sdk.modelcontextprotocol.io\&sz=32)

   MCP Python SDK

   +1

6. Phase 6 — 品質検証

   既知のノートを対象に、検索精度、出典一致率、処理時間、LLMに渡す入力トークン数を測定します。

## 6. Semantic Notes Vault MCPとの関係

ここは実装前に確認が必要です。既存プラグインがノート検索やリンク探索をすでに提供している場合、その機能を自作MCP Serverで重複実装する必要はありません。

* 既存プラグインが対応する検索・参照機能は再利用する。

* 不足する多言語Embedding、インデックス更新、出典管理だけを追加する。

* Ollamaとの接続と、ChatGPTなどからのMCP接続は別々に検証する。

OllamaのローカルAPIが利用可能であることと、ChatGPTからローカルMCP Serverを呼び出せることは別です。まずPC内で完成・検証し、その後、実際に利用するLLMクライアントとの接続を判断します。

## 7. 完成判定基準

この実装は、次の条件を満たした時点で初期版完成とします。

* Vaultの原文を変更せず、全ノートのインデックスを作成できる。

* 更新・削除されたノートを検出し、検索インデックスに反映できる。

* 日本語・英語の質問から関連ノートを検索できる。

* 検索結果から原文の所在と該当箇所を確認できる。

* MCPクライアントから5つのツールを呼び出せる。

* 検索対象を絞る前後で、入力トークン数と検索精度を比較できる。

最終判断： 16 GB RAMのWindows PCでは、`Ollama + Qwen3 4B + BGE-M3 + Chroma + SQLite + Python MCP Server` を初期構成とします。まず動作を安定させ、必要性を測定した上で8Bモデルへの変更を判断します。

なお、Semantic Notes Vault MCPの既存機能との重複を避けるため、最初の実装作業は、現在インストールしているプラグインの機能と接続方式の確認から始めるのが適切です。
