# 1. 最大の発想転換：「PROJECT仕訳」を廃止する

これは今回かなり重要です。

これまで、

```text
Daily Note
 ↓
PROJECT 01
PROJECT 02
PROJECT 03
...
```

という分類を考えていました。

しかし、

> MBT55 → AGRIX → HealthBook → PBPE

のように、一つの知識が複数Projectを横断するなら、**物理的に仕訳すること自体がKnowledge Architectureとして不自然**です。

そこで、

```text
Physical Location
        ≠
Knowledge Classification
```

とします。

### 物理ファイル

```text
2026-04-24_xxx.md
```

は一箇所だけ。

### Knowledge側

同じ内容から、

```text
PROJECT-01
PROJECT-02
PROJECT-03
```

への**多対多Relationship**を生成します。

つまり、

```text
1 Note
  ↓
many Knowledge Units
  ↓
many Projects
  ↓
many Domains
```

です。

これならタグ地獄を避けられます。

# 2. 「PROJECT」をフォルダではなくKnowledge Dimensionにする

さらに一歩進めます。

```text
PROJECT 01 HealthBook-MIOS
PROJECT 02 AGRIX
PROJECT 03 MBT55/MSC
PROJECT 04 PBPE
PROJECT 05 PMOS
PROJECT 06 BioNexus Integration
```

を、ファイル分類ではなく、

```text
Project Dimension
```

として扱います。

例えば、

```json
{
  "knowledge_unit": "KU-8F21",
  "project_affinity": [
    "PROJECT-01",
    "PROJECT-02",
    "PROJECT-03"
  ]
}
```

とする。

しかも、

```text
affinity = 0.92
```

のような数値を持たせることもできます。

ただし重要なのは、

**これはAIによる「事実上の分類」ではなく、検索・探索用の関連度である**

と明確に分離することです。

各Claimに単純な真偽値を与えない。

代わりに、

```text

├── EVIDENCE
├── DATE
├── ORIGIN
├── REPRODUCIBILITY
├── CONTRADICTION
├── STATUS
```

を持たせます。

さらに、

```text

```

を区別します。

これにより、

**「ChatGPTが昔書いた仮説」が、いつの間にか「BioNexusの事実」になる事故**

を構造的に防止できます。

# 5. 「Contradiction Engine」を中心機能にする

普通のRAGは、

> 質問 → 関連文書を検索

です。

BioNexusでは逆に、

> **知識同士が矛盾していないか？**

を常時検査させます。

例えば、

```text
Claim A
MBT55 = 55 species

Claim B
MBT55 > 120 species
```

なら、

```text
CONTRADICTION DETECTED
```

を生成する。

そして、

```text
Source A
Source B
Date A
Date B
Context A
Context B
```

を比較します。

これは現在のEvidence & Reconciliation思想とも完全に整合します。
