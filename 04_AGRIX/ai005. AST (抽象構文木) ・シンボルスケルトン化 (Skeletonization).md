もしくは、人が閲覧するリポジトリの内容とは別に、自然言語ではなく、AIが認識出来るコードなどに置き換え、アーキテクチャ構築に活かす手法があれば人にとって有益です。

---

まさに開発現場で急速に進化している「コードをAIが最も理解しやすい中間表現（中間表現データ）に変換してプロンプトやRAGに投入する」というアプローチです。

  

人間が読むソースコードには、インデント、変数の命名スタイル、コメント、冗長な構文など「AIの計算資源やコンテキスト領域を無駄に消費するノイズ」が多く含まれています。これをAIにとって密度が高く構造が明確な形式に圧縮・変換することで、16リポジトリもの巨大なコードベースでも読み飛ばしなく完璧に全体アーキテクチャを理解させることが可能になります。

  

人間にとっても有益な、代表的な「AI向け中間表現・構造化変換手法」を4つ紹介します。

  

### 1. AST (抽象構文木) ・シンボルスケルトン化 (Skeletonization)

関数の「中身の実装ロジック」をすべて削ぎ落とし、「クラス定義、メソッド署名（引数と返り値）、型情報、モジュールのExport/Import」だけを残した「骨組み（スケルトン）」に変換する手法です。

  

- **人間のコード (TypeScript/Pythonなど)**
    
    数百行の複雑なバリデーションや例外処理、ログ出力が書かれている。
    
      
    
- **AI向けスケルトンコード**
    
      
    
    TypeScript
    
    ```
    // repo-auth/src/services/auth.service.ts
    export class AuthService {
      constructor(private readonly userRepo: UserRepository, private readonly jwtService: JwtService) {}
      public async validateToken(token: string): Promise<UserPayload>;
      public async issueToken(user: User): Promise<AuthTokens>;
    }
    ```
    
- **効果:** コードのデータ量を**80%〜90%削減**しながら、アーキテクチャ分析に必要な「インターフェース」と「依存関係」の情報量を100%維持できます。16リポジトリのスケルトンであれば、1つのコンテキストに余裕で収まります。
    
      
    

### 2. SCIP / LSIF（コードインデックス形式）への変換

Sourcegraphなどが開発している **SCIP (Source Code Intelligence Protocol)** や **LSIF** は、コードの定義・参照・型情報をプログラミング言語非依存の構造化データ（Protobuf / JSON）に変換する形式です。

  

- **特徴:** 「どのファイルのどの関数が、別リポジトリのどのAPIを呼んでいるか」という**精密な参照グラフ**が機械読み取り可能な形式で出力されます。
    
      
    
- **活用法:** AIにソースコード本文を読ませるのではなく、このSCIP/LSIFデータ（またはそれを変換したテキスト）を読み込ませることで、AIは「依存関係のグラフ構造」としてシステム全体を即座にトポロジー理解します。
    
      
    

### 3. Tree-sitter を使った DSL / ナレッジグラフ化

解析パーサーライブラリ **Tree-sitter** を使い、16リポジトリのコードを自作の簡潔なDSL（ドメイン固有言語）や、Mermaid / PlantUML などのダイアグラム言語に事前変換してしまう手法です。

  

- **変換プロセスの例:**
    
      
    
    1. ローカルスクリプトで16リポジトリのコードをTree-sitterで構文解析する。
        
          
        
    2. 「リポジトリAのService Xが、リポジトリBのAPI Yを呼び出している」という関係性だけを抽出。
        
          
        
    3. 以下のような**アーキテクチャ記述テキスト**を自動生成してGeminiに渡す。
        
          
        
    
    Plaintext
    
    ```
    [Service: repo-order/OrderService]
      - calls -> [API: repo-payment/PaymentApi/charge] (Protocol: gRPC)
      - uses  -> [DB: OrdersTable] (Type: PostgreSQL)
    ```
    
- **効果:** 自然言語や生のコードよりも圧倒的に情報密度が高く、Geminiが「ハルシネーションを起こす余地」を完全になくすことができます。
    
      
    

### 4. Code Summarization (階層型コードサマリー) の自動構築

AI（小型・高速なローカルモデルやGemini Flash等）を使って、コードを階層的に圧縮・中間言語化する手法です。

  

1. **ファイル単位:** 各ファイルの実装を100文字程度の「機能・入出力仕様（JSON形式）」に自動圧縮。
    
      
    
2. **ディレクトリ単位:** ファイル群のサマリーをまとめて「モジュールの役割」に自動圧縮。
    
      
    
3. **アーキテクチャ構築用AI（Gemini Pro等）へ:** 圧縮された「サマリーの木構造」だけを入力する。
    
      
    

### 実践するならどの方法が一番早いか？

最も簡単かつ効果的なのは **「1. スケルトン化（型とインターフェースのみの抽出）」** です。

  

たとえば、Pythonなら `ast` モジュール、TypeScriptなら `typescript` コパイラAPIや `ts-morph` などのCLIツールを使って、数行のスクリプトで「関数の実装の中身（body）を取り除いて型定義だけ出力する」処理を16リポジトリにかけるだけで、AIの読み取り精度は別次元に向上します。
