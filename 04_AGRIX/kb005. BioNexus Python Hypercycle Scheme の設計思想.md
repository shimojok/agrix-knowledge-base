## 1. BioNexus Python Hypercycle Scheme の設計思想

ハイパーサイクル（Hypercycle）理論において、各自己複製系（反応）の生成物が次の反応の触媒となり、全体として閉じた超循環を形成します。本スキームでは、これをデータと計算モデルの循環として再現します。


```Plaintext
       [ 事象 (Event/Input) ] 
            │  (問診揺らぎ / 土壌センサー / 物質投入)
            ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 1: Signal Sensing (RAG Local Engine)              │
│  - 関連ノート/コードのベクトル検索 & 関連文脈の触媒抽出  │
└──────────────────────────┬───────────────────────────────┘
                           │ 抽出されたノード・パラメータ
                           ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 2: Metabolic Transformation (Python Code Engine)   │
│  - Pydantic v2 スキーマによる確実な型決定                │
│  - ODE Solver / 代謝ネット演算による決定論的数値導出    │
└──────────────────────────┬───────────────────────────────┘
                           │ 導出数値 (SCFA/ATP/炭素固定量/取引価値)
                           ▼
┌──────────────────────────────────────────────────────────┐
│  Phase 3: Hypercyclic Coupling (Data Pipeline)          │

│  - 土壌代謝 ➔ 食・生薬 ➔ 腸内細菌 ➔ 内分泌/ATP への伝達  │
└──────────────────────────┬───────────────────────────────┘
                           │ 統合表現形式
                           ▼
       [ 成果 (Outcome/JSON Schema) ] 
            │  (agrix-platform-kb.json / healthbook-platform-kb.json)
            └─────────► 新たなナレッジとして RAG へ還元 (循環完了)
```

1. **事象 (Event/Input):** ユーザーからの多次元問診、土壌データ、資材投入量などの初期入力。
    
2. **数値 (Metric/Transformation):** 常微分方程式（ODE）や確定型アルゴリズムにより導出される数値（SCFA生成量、GLP-1分泌効率、ミトコンドリアATP効率、炭素固定量 $5.8\,\text{tCO}_2\text{e/ha/年}$ など）。
    
3. **テクノロジー (Coupled Pipeline):** 単体コード群がネットワーク化され、入力された数値を次の処理（AGRIX ➔ HealthBook）の決定論的変数として受け渡すシステム。
    
4. **成果 (Outcome/JSON):** 最終的な知識構造体（`agrix-platform-kb.json` / `healthbook-platform-kb.json`）の自律的生成と、RAGインデックスへのフィードバック。

from datetime import datetime

from pydantic import BaseModel, Field

TInput = TypeVar("TInput")
TOutput = TypeVar("TOutput")

### (2) HealthBook 領域: 全代謝経路・ATP・内分泌計算ノード (`src/bionexus_kb/healthbook/pathways/atp_engine.py`)


```Python
from pydantic import BaseModel, Field
from bionexus_kb.core.base_model import BaseHypercycleEngine, HypercycleNodeResult

class MetabolicInput(BaseModel):
    scfa_acetate_mM: float = Field(..., description="酢酸濃度 (mM)")
    scfa_butyrate_mM: float = Field(..., description="酪酸濃度 (mM)")
    phytochemical_index: float = Field(..., description="ファイトケミカル活性指数 (0.0-1.0)")

class MetabolicOutput(BaseModel):
    mitochondrial_atp_yield: float = Field(..., description="推定ATP産出効率 (%)")
    glp1_secretion_relative: float = Field(..., description="GLP-1分泌刺激相対値")
    orp_optimization_score: float = Field(..., description="ORP(酸化還元電位)最適化スコア")

class MetabolicPathwayEngine(BaseHypercycleEngine[MetabolicInput, MetabolicOutput]):
    node_id = "healthbook.pathways.atp_engine"

    def process(self, input_data: MetabolicInput) -> HypercycleNodeResult[MetabolicInput, MetabolicOutput]:
        # 決定論的な数理・物理化学モデルに基づく計算
        # 酪酸およびファイトケミカルによるATP産出効率向上
        atp_boost = (input_data.scfa_butyrate_mM * 0.15) + (input_data.phytochemical_index * 20.0)
        base_atp_yield = min(100.0, 70.0 + atp_boost)

        # 腸管内分泌細胞(L細胞)のGLP-1刺激計算
        glp1_signal = (input_data.scfa_acetate_mM * 0.4) + (input_data.scfa_butyrate_mM * 0.8)

        # ORP最適化スコア
        orp_score = min(1.0, 0.5 + (input_data.phytochemical_index * 0.5))

        metrics = MetabolicOutput(
            mitochondrial_atp_yield=round(base_atp_yield, 2),
            glp1_secretion_relative=round(glp1_signal, 2),
            orp_optimization_score=round(orp_score, 2)
        )

        return HypercycleNodeResult(
            node_id=self.node_id,
            input_state=input_data,
            computed_metrics=metrics,
            metadata={"source": "AKG019/AKG020 Metabolic Integration"}
        )
```

## 4. このアーキテクチャがもたらすメリット

1. **生成AI依存からの完全脱却（決定論的精度）**
    
    - LLM（チャットAI）はコードの記述とRAG文脈の検索・要約に専念させ、数値導出や生化学・経済計算はすべて型安全な Python スキーム（Pydantic + Engine）上で実行します。ハルシネーションは物理的に排除されます。
        
2. **モジュール性と自己進化性（ハイパーサイクルの接続）**
    
    - 個々の Python コードは単一の微生物のように独立しつつ、インターフェースが共通化されているため、パイプライン上で結合して「事象 ➔ 土壌 ➔ 作物 ➔ 人体代謝 ➔ 経済価値」の循環計算を1連の流れとして実行できます。
        
3. **70%:30% 構成の厳格な構造維持**
    
    - AGRIX (70%) プラットフォームと HealthBook (30%) プラットフォームが独立したモジュール構造として維持されつつ、成果物である JSON ファイル（`agrix-platform-kb.json` / `healthbook-platform-kb.json`）が決定論的に更新・出力されます。
