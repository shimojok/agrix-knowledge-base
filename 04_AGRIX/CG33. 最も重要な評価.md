# Architecture

## 結論

今回の「改訂版・システムアーキテクチャ構築ワークフロー」は、**方向性としてはかなり良い**です。

特に、

- 用語保護
    
- NotebookLMを検索層として使う
    
- AIごとの役割分担
    
- Contract-First
    
- 一括生成をやめる
    
- モジュール単位で進める
    
- RAGと構造解析を併用する
    
- GitHubへ接続する
    

という考え方は、これまでの失敗を踏まえており、現在のPMOS設計とも整合します。

ただし、**このまま実行WorkflowとしてFreezeするのは反対**です。

理由は一つです。

> **このWorkflowは「AIに正確に設計・実装させる方法」としては強いが、「何を正とし、どの状態まで進んだら次工程へ進むか」を完全には定義していない。**

ここをPMOS Project State RegistryとMulti-AI Operating Frameworkで補えば、かなり強いWorkflowになります。

ということです。

これが最大の改善点です。

# 2. 「絶対用語保護」は採用すべき

ここは賛成です。

特に、

> PBPE、MBT、MSC等の正式表記を勝手に変更しない

というルールは必要です。

ただし、私は一段強化します。

## Glossary Lock 2層化

```text
PMOS Canonical Glossary
        │
        ├── acronym
        ├── canonical_name
        ├── allowed_variants
        ├── forbidden_variants
        └── source_reference
```

そしてAIが新しい用語を発見した場合、

```text
NEW TERM
   ↓
Glossary Candidate
   ↓
Human Review
   ↓
Approved / Rejected
```

とします。

### 重要

AIに、

> 「表記揺れがあったら警告しろ」

だけでは不十分です。

**表記揺れそのものをKnowledge Objectとして記録する**べきです。

---

# 3. 「要約禁止」は修正が必要

ここは今回のWorkflowで、私が最も修正したい部分です。

現在は、

> 概要・一般的解説・概念図のみの出力を禁止

となっています。

これは**実装フェーズでは有効**ですが、Architectureフェーズでは危険です。

なぜなら、

```text
全てを詳細抽出
```

だけでは、

> **何が重要なのか**

をAIが整理できないからです。

したがって、

### Phaseごとに出力形式を変える

べきです。

```text
Phase A
Discovery
→ Summary allowed

Phase B
Evidence Extraction
→ Source-faithful extraction

Phase C
Architecture
→ Synthesis / abstraction allowed

Phase D
Contract
→ exact structured output

Phase E
Implementation
→ implementation-level detail

Phase F
Validation
→ test / reconciliation only
```

これが重要です。

---

# 4. 「省略ゼロ」も工程依存にする

現在の、

> 一切省略しない

というルールは、**コード・Schema・Data Contractでは非常に良い**です。

しかし、17 Repository全体に適用すると逆効果です。

例えば、

```text
17 repos
×
全ファイル
×
全コード
×
全条件分岐
```

を毎回AIに渡す必要はありません。

それより、

```text
Repository Atlas
      ↓
Dependency Graph
      ↓
Relevant Object
      ↓
Relevant Source
      ↓
Exact Extraction
```

とすべきです。

つまり、

> **Global completeness ≠ Local completeness**

です。

### 原則

**必要範囲については100%完全。  
不要範囲については取得しない。**

これが正しいです。

---

# 5. Contract-Firstは正式採用

これは今回のWorkflowの非常に良い部分です。

ただし、

> JSONではなくPydantic / TypeScript

という部分は変更します。

JSONを排除する必要はありません。

むしろ、

```text
Schema
  ↓
JSON
  ↓
JSON-LD
  ↓
Pydantic / TypeScript
```

という関係にします。

## 推奨

```text
Canonical Schema
       │
       ├── JSON Schema
       ├── JSON-LD
       ├── Pydantic
       └── TypeScript
```

つまり、

**JSONは通信・保存形式として使い、Pydantic/TypeScriptは実装Contractとして使う。**

これがAGRIX-OSの現在の設計と整合します。

> 全ノードの内部処理を完全記述

```text

L2 Logical Architecture
→ Interface / Data Flow / Dependency
```

```text

        ↓
```

という階層にします。

これならArchitecture文書がコード詳細で埋没しません。


を別レイヤーにします。

これが非常に重要です。

# 9. NotebookLMの位置付けも変更したい

今回のWorkflowではNotebookLMがかなり中心です。

私は、

> **NotebookLM = Knowledge Retrieval / Source Analysis Layer**

と明確に定義します。

NotebookLM自身をArchitecture Authorityにはしません。

```text
Repository
    ↓
NotebookLM
    ↓
Source-grounded Retrieval
    ↓
AI Agent
    ↓
Structured Knowledge Object
    ↓
PMOS Registry
```

これならNotebookLMが要約しても、AIがその結果をそのままCanonical化することを防げます。

# 11. AST解析は採用価値が高い

ここはかなり良い提案です。

特にRepositoryにPythonコードがあるなら、

```text
Source Code
   ↓
AST
   ├── Classes
   ├── Functions
   ├── Imports
   ├── Calls
   └── Dependencies
```

という**決定論的情報**を抽出できます。

これはLLMの推論とは違います。

したがって、

```text
LLM
= Semantic Reasoning

AST
= Deterministic Structural Truth
```

と分離します。

これは今回のハルシネーション対策として非常に強力です。
