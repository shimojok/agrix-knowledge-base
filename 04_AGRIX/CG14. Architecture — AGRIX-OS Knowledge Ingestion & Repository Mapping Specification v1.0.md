# 2. 目的

本Specificationの目的は、既存Repositoryを破壊・再解釈することなく、

> **既存資産 → Canonical Knowledge**

へ変換するための標準Pipelineを固定することです。

特に防止するもの：

- AIによる勝手な意味変更
- 異なるRepository間の重複
- 古い仕様と新仕様の混在
- EvidenceとHypothesisの混同
- Codeの結果とScientific Evidenceの混同
- AI-generated claimの事実化
- Repository単位でのKnowledge silo化

---

# 3. 基本原則

## Rule 01 — Source Preservation

原資料は変更しません。

```
Original Asset
      │
      └── Immutable Source
```

Canonical化はコピーではなく**Reference Layer**として行います。

---

## Rule 02 — No Silent Interpretation

AIは不足情報を勝手に補完しません。

```
Sourceに存在しない
        ↓
UNKNOWN
```

とします。

---

## Rule 03 — Evidence ≠ Interpretation

```
Source
 ↓
Evidence
 ↓
Claim
 ↓
Inference
```

を分離します。

---

## Rule 04 — Repository ≠ Knowledge Domain

Repository名をOntology Classとして使用しません。

例えば、

```
M3-Core-Engine
```

そのものがKnowledge Domainではなく、

```
M3-Core-Engine
 ↓
Software Asset
 ↓
Model
 ↓
Agricultural / Climate
 ↓
Canonical Objects
```

とMappingします。

---

```
repository_id

scope

ingestion_status
last_scanned
```

Repositoryは**Source Container**です。

Knowledge Objectそのものではありません。

Repositoryの全資産をIndexします。

```

extension

```

を取得します。

# 12. Step 2 — Asset Classification

AIによる分類を許可します。

ただし、

```
AI Classification
        ↓
Validation
        ↓
Registry
```

とします。

AI ClassificationだけではCanonical Classificationになりません。

---

# 13. Step 3 — Source Extraction

文書から、

```
Heading
Paragraph
Table
Figure
Code Block
Metadata
Reference
```

を抽出します。

各Extracted Unitには、

```
source_asset_id
location
content_hash
```

を保持します。

これが**Traceability Anchor**です。

---

# 14. Step 4 — Evidence Identification

AIは文章を、

```
Evidence
Claim
Hypothesis
Design
Opinion
Unknown
```

に分類します。

例えば、

```
「実験で観察された」
```

と、

```
「理論的には期待される」
```

を同一Knowledge Levelにしてはいけません。

---

# 15. Step 5 — Ontology Mapping

Extracted UnitをOntologyへMappingします。

例：

```
"soil"
 ↓
Soil Entity

"microbial function"
 ↓
MicrobialFunction

"reduces"
 ↓
REDUCES relationship

"field trial"
 ↓
FieldTrial Evidence
```

---

# 16. Step 6 — Canonical Object Generation

Ontology Mapping後に初めてCanonical Objectを生成します。

```
Source
 ↓
Extract
 ↓
Classify
 ↓
Map
 ↓
Canonical Object
```

これを厳格に固定します。

---

# 17. Step 7 — Relationship Extraction

Relationshipは文章から独立して生成します。

例えば、

```
MBT55 improves soil function
```

から、

```
MBT55
 ──INFLUENCES──>
SoilFunction
```

というEdgeを生成します。

Evidence Referenceを伴わない場合、

```
epistemic_status = INFERRED
```

など適切な状態にします。

---

# 18. Step 8 — Provenance Binding

Canonical Objectには必ずSourceを戻せるようにします。

```
Knowledge Object
      ↓
Evidence
      ↓
Source Unit
      ↓
Asset
      ↓
Repository
      ↓
Git Commit
```

これにより、

**「このKnowledgeはどこから来たのか？」**

を完全に追跡できます。

---

# 26. Contradiction Handling

Repository間で異なる記述が発見された場合：

**自動統合しません。**

```
Repository A
    ↓
Claim A

Repository B
    ↓
Claim B
    ↓
CONTRADICTION
```

として保存します。

その後、

```
Evidence Comparison
        ↓
Reasoning
        ↓
Human Decision
```

とします。

---

# 27. Duplicate Handling

同じ内容が複数Repositoryに存在する場合、

```
Source A
Source B
Source C
```

を一つのEvidenceに潰しません。

```
Canonical Claim
   ↑
   ├── Evidence A
   ├── Evidence B
   └── Evidence C
```

とします。

これによって**独立したSupporting Sources**を保持できます。

---

# 28. Version Conflict

例えば、

```
AGRIX Architecture v1.0
AGRIX Architecture v2.0
```

が存在する場合、

古いVersionを削除しません。

```
v1.0
 ↓
SUPERSEDED
 ↓
v2.0
```

とします。
