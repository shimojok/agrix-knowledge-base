## 2. なぜ各AIが挙動不審になったのか（技術診断）

お送りいただいた資料から、**5つの構造的原因**が特定できます。

### 原因①：コンテキストの物理的限界

| 項目 | 数値 |
|------|------|
| Vaultノート数 | 約6,770 |
| 全体サイズ | 数百MB〜GB規模 |
| 平均チャットのコンテキスト上限 | 128K〜200Kトークン |

**結論**：Vault全体を1つのチャットに読み込むことは**物理的に不可能**。部分的に読み込んでも、**次のターンで圧縮・忘却**される。これがすべての根っこ。

### 原因②：役割の混同（Vault vs 実行環境 vs リポジトリ）

| 要素 | 実体 | AIの誤認 |
|------|------|----------|
| agrix-knowledge-base | Obsidian Vault（知識） | 「Pythonプロジェクト」と誤認 |
| bionexus-engine | Python実行環境 | 「Vaultの一部」と誤認 |
| 17リポジトリ | 過去の実装資産 | 「新規作成すべき」と誤認 |

→ **パス幻覚・フォルダ構造矛盾**の直接原因（W009→W013で発生）

### 原因③：設計スパイラル（ChatGPTの事例）

```
設計 → 「もっと良い設計は？」→ 再設計 → 「さらに…」→ 無限ループ
```
- 出力が「設計案」ばかりで**コードに到達しない**
- ユーザーが「実装して」と言っても、また設計に戻る
- **LLMの「完璧主義バイアス」**：不確実性を埋めようとして設計を繰り返す

### 原因④：メタデータ設計の混乱（AKG010〜AKG013）

- 「タグ不要論」→「でもメタデータは必要」→「Pythonで動的生成」
- この議論自体が**LLMの混乱を増幅**
- **本質**：Obsidianのタグ（人間用）とRAGのメタデータ（AI用）は**別物**。混同すると設計が迷走

### 原因⑤：2スレッド体制の副作用

| スレッド | 役割 | 副作用 |
|----------|------|--------|
| 開発スレッド | 実装 | **構造を記憶できない**。毎回パスを再推測 |
| コンテキスト最適化 | 圧縮 | 成果物が**開発スレッドに正しく伝わらない** |

→ 2スレッド間で**情報の非対称性**が生じ、開発スレッドが誤推測を始める

## 4. DeepSeek（本スレッド）が取るべきアプローチ

これまでの失敗を踏まえ、本スレッドは**以下の原則**で進めます。

### 原則①：構造を外部化する（記憶しない）

- Vault＋bionexus-engine＋17リポジトリの構造を、**このスレッドに固定表として明記**
- 毎回参照する。LLMの記憶に頼らない
- **Dailynote目次を「構造の唯一の情報源」とする**

### 原則②：設計スパイラルを禁止する

- 「完璧な設計」を目指さない
- **最小実装→動作確認→拡張**のサイクル
- 各ターンで**必ず動くコードまたは固定データを出力**

### 原則③：役割を厳密に分離する

| 要素 | 役割 | 配置 |
|------|------|------|
| Vault | 知識 | `agrix-knowledge-base/` |
| 実行環境 | コード | `bionexus-engine/` |
| リポジトリ | 過去資産 | GitHub（Vault外） |
| データ | JSON | Vault内 `data/` |
| 本スレッド | PMO | 構造固定・検証・設計 |

### 原則④：ハルシネーションを構造的に防ぐ

- **パス検証スクリプト**を必ず実行
- **Vault原文の引用**を必須化
- **Dailynoteに設計判断を記録**し、履歴を追跡

### 原則⑤：段階的に進める

- Phase 1：構造の固定（現在ここ）
- Phase 2：RAGインデックス構築
- Phase 3：シミュレーション構築
- Phase 4：公開層（ビル・ゲイツ氏向け）
