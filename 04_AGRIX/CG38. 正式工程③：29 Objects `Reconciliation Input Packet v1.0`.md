# 2. 重要な実行原則

今回、特に以下を固定します。

### A. Canonical Objectは変更しない

```text
Canonical Dataset v1.0
        ↓
READ ONLY
        ↓
Reconciliation Input
```

現在のObjectをReconciliation用にコピーします。

---

### B. Evidenceを新規に「創作」しない

RAG検索で見つからないものについて、

> 「おそらくこのRepositoryにあるはず」

とはしません。

```text
Evidence Found
     ↓
Input Packet

Evidence Not Found
     ↓
MISSING_EVIDENCE
```

です。

---

### C. RAG検索順位をEvidence強度と混同しない

```text
retrieval_score
      ≠
evidence_strength
```

これはInput Contract v1.0の重要ルールです。

---

### D. ASTはコードが存在する場合だけ使用

Python等の構造化コード：

```text
AST → Structural Evidence
```

文書・Markdown・JSON：

```text
Document Parser → Semantic Evidence
```

という形で分離します。

# 4. Claim生成について

ここは今回の重要工程です。

既存Objectに含まれる説明を、そのまま1つの巨大なClaimにしません。

例えば、

```text
Object
│
├── Claim A：Architecture
├── Claim B：Function
├── Claim C：Data Flow
├── Claim D：Implementation
└── Claim E：Evidence
```

というように、**Reconciliation可能な単位に分解**します。

ただし、元資料に書かれていないClaimをAIが追加することは禁止します。

---

# 5. RAG Retrieval

各ClaimについてLocal RAGに検索要求を出します。

概念：

```text
Claim
  │
  ├── exact terminology search
  ├── semantic search
  └── repository metadata filter
             │
             ▼
        Candidate Evidence
```

検索結果は、

```text
source_id
file_path
chunk_id
retrieval_score
```

を持ってPacketに格納します。

---

# 6. AST Retrieval

コードに関連するClaimについては、

```text
Claim
 ↓
Repository
 ↓
Module
 ↓
Class / Function
 ↓
Call / Import / Dependency
```

を検索します。

これにより、

> 「この機能があるとAIが説明した」

ではなく、

> 「このFunctionが実際に存在する」

という構造Evidenceを取得できます。
