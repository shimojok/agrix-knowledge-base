AGRIXおよびHealthBookシステム構築プロジェクトの成功に向け、ご提示いただいた新しい順序・ご指定の原則・Kimi（Moonshot AI）の特性分析を反映させた「改訂版・システムアーキテクチャ構築ワークフロー」を提示します。

### 原則指示の適用：絶対用語保護ルール（Glossary Lock）

AIによる勝手な用語改変は、システムの概念的整合性を破壊します。エージェントおよびNotebookLMに与える**全プロンプトの先頭に以下のガード節を強制注入**します。

  
```Plaintext
======================================================================
【絶対遵守ルール：アクロニムおよび英語表記の改変禁止】
1. 本プロジェクトの略称（PBPE, MBT, MSC 等）を展開・記述する際、
   ソース（リポジトリテキスト）内に存在する『正式な英語表記』を1文字たりとも改変・pp言い換え・独自解釈しないでください。
   （例：PBPEの英語表記を、ソース内に存在しない別の英単語へ置き換える行為は固く禁止します）

2. ソーステキスト内に、同一略称に対する異なる英語表記や表記揺れが存在する場合は、
   回答の冒頭で必ず『【警告】リポジトリ内英語表記不一致検出: [発見した英語表記一覧] (対象ファイル/箇所)』と報告してください。

【出力基本方針：要約および省略の絶対禁止】
・「概要」「一般的な解説」「概念図のみの出力」は一切禁止します。
・`// TODO` や `pass`、`〜以下省略〜` などの省略記法は禁止し、ソース内に存在する計算ロジック、データ型、条件分岐（if/else）の全ステップを省略せずに抽出・出力してください。
======================================================================
```

### 1. 生成AIがNotebookLMに行う「メタ検索指示（Meta-Prompting）」

AIエージェント（ChatGPT等）がNotebookLMに対して直接投入させるための高密度・非圧縮型検索指示を生成します。

- **構造指定型抽出指示（Structural Extraction）:**
    
    要約（Summary）を明示的に禁止し、パラメータ、条件式、型情報のみを1文字も削らずに抽出させます。
    
    > **プロンプト指示例:**
    > 
    > 「PBPE/MBT55モジュールにおける『基質変化率計算』の記述をすべて抽出してください。要約や一般的な解説は一切不要です。原文に含まれる入力変数名、型、計算式、条件分岐（if/else）の全ステップのみを箇条書きで全件出力してください。」
    > 
- **カスケード型検索（Cascading Search Query）:**
    
    全体を一度に引かず、依存関係順（親→子→孫）に検索クエリを分割・連続投入します。
    
    > **ステップ1:** 「MSCハイパーサイクル層を構成する全インターフェースのリストのみを出力してください。」
    > 
    > **ステップ2:** 「ステップ1で抽出された `IHypercycleNode` のメソッドシグネチャとパラメータ制約のみを抽出してください。」
    > 
### 2. NotebookLMの出力制限を破る「分割・深度指定（Chunk & Depth Control）」

NotebookLMの「モデルや概要だけ示して終わりたがる」抽象化バイアスを、プロンプトの深さ指定で破壊します。

- **「実装レベル記述」の強制:**
    
    > 「概念図や概要の説明はスキップしてください。データ構造をPython Pydanticクラス、ロジックを条件分岐付き疑似コードで記述し、内部処理フローを一行も省略せずに記述してください。」
    > 
- **セクション指定の出力分割:**
    
    > 「全体を出力しようとせず、本指示では『PBPEデータ同期パイプラインの例外ハンドリング層』のみを極限まで詳細に出力してください。出力が完了したら『[SECTION_1_COMPLETE]』と最後に出力してください。」
    > 
### 3. ハルシネーションを防ぐデータ入出力フォーマット（エージェント & NotebookLM共通）

指示を出すAIエージェント、および指示を受けて出力するNotebookLMの**双方が遵守すべき厳格なデータ交換規格**です。

- **Contract-First (Python Pydantic / TypeScript Protocol):**
    
    データ構造の伝達にはJSONではなく、バリデーションロジックやDocstringを埋め込んだ型定義コードを使用します。
    
    > **フォーマット出力指定:**
    > 
    > ```Python
    > class MBT55SubstrateContract(BaseModel):
    >     """PBPE/MBT55における代謝反応パラメータ契約"""
    >     substrate_id: str = Field(..., description="基質識別子")
    >     concentration: float = Field(..., ge=0.0, le=100.0, description="濃度(mM)")
    >     
    >     @field_validator('concentration')
    >     def check_limit(cls, v):
    >         # 臨界値80.0mM超過でMSCハイパーサイクル抑制フラグが発動するロジックを実装すること
    >         return v
    > ```
    
- **Mermaid.js + 逐条解説プロトコル:**
    
    図解出力時には、必ず図中の「すべてのノード」に対する内部処理ステップの全文記述を強制します。
    
    > **フォーマット出力指定:**
    > 
    > `[Mermaid図]` を出力した後、図に含まれる全ノード（`NodeA`, `NodeB`...）について以下の項目を例外なく全記述させる。
    > 
    > ・ノードID / 入力データ型 / 内部処理アルゴリズム（全ステップ） / 出力データ型 / エラー処理
    > 
### 4. AIエージェント（Claude, Gemini, ChatGPT, Kimi）の「役割分担型」活用

ご指定の特性を踏まえ、長文文脈保持（Long Context）と推論能力に長けた **Kimi（Moonshot AI）** を新たに組み込んだマルチエージェントオーケストレーション体制です。

#### Kimiの特性・強み分析

- **長文コンテキスト処理と忠実な文脈保持（200万トークン級）:** 超長文のドキュメントやコードを読み込んでも、指示を無視しにくく文脈を落とさない。
    
- **構造化テキスト・コードの精密パース:** 大規模なテキストデータから正確な依存関係を抽出し、正確なドキュメント・変換コードへ再構成する能力が高い。

### 統合運用イメージ

1. **ChatGPT** が、NotebookLMに検索させるための「メタプロンプト（用語保護・Contract-First指定付き）」を生成。
    
2. **NotebookLM** が、17のリポジトリ（.txt）から「用語不一致の有無」を報告しつつ、省略のない型定義＋逐条解説データを抽出。
    
3. **Kimi** が、抽出されたデータと未解決の課題から、「仮説に基づく先端的な新論理・アーキテクチャ拡張案」を構築。
    
4. **Claude 3.5 Sonnet** が、その論理と型定義を元に、省略ゼロの実装コード・詳細設計ドキュメント・ダッシュボード構成を出力。
    
5. **Gemini** が、出来上がった生成物が全体設計および用語指定（PBPE/MBT/MSC等）に違反していないかを全数監査。
    
この体制により、AIの要約癖・勝手な用語改変・ハルシネーションを物理的に防ぎながら、仮説ベースの先端アーキテクチャ構築を加速させることができます。

### 5. Pinecone不要：Python＋ローカル軽量ベクトル検索（RAG）の自動化

Pineconeのような外部DBサービスで頓挫した背景を鑑み、インフラ構築不要なローカルPythonスクリプトによるRAG（検索拡張生成）へ移行することを強く推奨します。

- **ChromaDB / FAISS + LangChain（完全ローカル/軽量）:**
    
    Pythonスクリプトを数行書くだけで、17のリポジトリ（.txt）をローカル環境でベクトル化・保存できる「ChromaDB」を構築します。外部サーバーの管理が不要でエラーリスクが劇的に下がります。
    
- **AST（抽象構文木）解析による精密データ伝達:**
    
    ベクトル検索（意味検索）だけでなく、Pythonの`ast`モジュールを使ってコードから「関数名・クラス名・依存関係」の決定的な木構造テキストを自動抽出し、それをAIエージェントのコンテキストに注入します。ハルシネーションが物理的に発生しなくなります。
    
### 6. 今後のプロジェクト中断を防ぐ「統合運用戦略」

上記の手法を組み合わせた、最も安全かつ再現性の高い新しいワークフローです。

```
[17の.txtリポジトリ]
       │
       ├─► ① Gemini (全テキスト一括読み込み) ──► 「全体依存関係マップ (Graph.md)」を生成
       │
       ├─► ② ローカルPython (ChromaDB/AST) ──► コードの精密検索エンジンとして機能
       │
       └─► ③ NotebookLM (ドキュメント群) ──► 詳細仕様の抽出用データベース
               │
               ▼ (検索・抽出指示)
       ④ Claude 3.5 Sonnet (メイン実装)
         └─► Contract-First形式で「一切省略のない詳細ドキュメント・コード」を順次生成
```

1. **「一括生成」を捨てる:** 1つのプロンプトで大規模なドキュメントを作らせようとせず、依存関係マップ（Graph）に基づき、**1モジュールずつ（1ファイルずつ）完全に完成させていく**。
    
2. **型（Contract）を先に固定する:** MBT55やハイパーサイクルの共通仕様部分を、まずPythonの`dataclass`や`Pydantic`で完全に固定し、その「型ファイル」を常にAIのシステムプロンプト（参照前提）に含めることで、微細なズレの増幅を完全に遮断します。
    
この「ローカル軽量RAG＋役割分離マルチエージェント＋型定義先行アプローチ」により、インフラの構築コストを最小限に抑えつつ、限界を超えた密度の高いドキュメントとコードの自動生成が可能になります。
