## **GitHubには PDF・HTML をそのままプッシュして OK。**

## **しかし、txt化するタイミングは “NotebookLM と RAG に入れる直前” が正しい。**

つまり：

- GitHub → **PDF/HTMLのまま保存（成果物として）**
    
- Repomix → **PDF/HTMLを含めてパッキング（XML化）**
    
- NotebookLM → **XML→txt に変換してアップロード**
    
- ローカルRAG → **txtフォルダに入れる（検索対象）**

# 🟦 なぜ GitHubには PDF/HTML をそのまま置くのか？

### ✔ 1. GitHubは「成果物の保管場所」

PDFやHTMLは **成果物（ダッシュボード・スライド）** なので、GitHubに置くことで：

- バージョン管理
    
- 参照性
    
- Microsoft技術者への共有
    
- Azureデプロイ準備
    
- NotebookLMの出典として利用可能
    

すべてが一貫します。

### ✔ 2. GitHub → Repomix の流れが最も安定

Repomixは **GitHubのフォルダ構造を維持したままパッキング**できるため、 NotebookLMが理解しやすい構造になります。

# 🟦 txt化のタイミングは「NotebookLMとRAGに入れる直前」

Kaz、ここが最も重要です。

## ❌ 間違ったタイミング

- GitHubにプッシュする前に txt化
    
- PDF/HTMLを手動で txt化して GitHubに置く
    
- PDF/HTMLをRAGに直接入れる
    

これらは **すべて誤り**です。

## ✔ 正しいタイミング

### **① GitHubに PDF/HTML をそのまま置く（成果物として）**

### **② Repomixでパッキング（XML化）**

### **③ XML → txt に変換（NotebookLM用）**

### **④ txt をローカルRAGの /txt フォルダに入れる**

この順番が **最も壊れない**。

# 🟩 なぜ txt化は「最後」にするのか？

### ✔ NotebookLMは「テキストだけ」をベクトル化する

PDFやHTMLはそのままでは NotebookLM が読めません。

### ✔ RAGも「テキストだけ」を検索する

PDFやHTMLはそのままでは意味検索できません。

### ✔ Repomixは「構造を維持したままテキスト化」できる

Repomixは：

- HTMLのテキスト部分
    
- PDFのテキスト部分
    
- Markdown
    
- README
    
- コード
    
- コメント
    
- 設計書
    

を **階層構造を維持したまま XML にまとめる**。

その後、XML → txt に変換すれば、 NotebookLMもRAGも **正しく理解できるテキスト**になります。
