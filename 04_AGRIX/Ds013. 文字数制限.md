## 2. PMOは務まるか？ — 条件付きで「務まる」

### 務まらないケース

- **全Vault・全リポジトリをこのチャットに読み込ませる** → 100%失敗します
- **1つのチャットで数週間〜数ヶ月の設計を継続** → コンテキスト上限で必ず破綻します
- **巨大ファイル（ツリー全体、全ノート）を貼り付ける** → 即座に上限到達

### 務まるケース（推奨）

- **「構造の唯一の情報源」を別ファイル（Dailynote）に置き、このスレッドは参照のみ**
- **大きなファイルは要約・抽出してから送る**（全文貼り付け禁止）
- **チャットを「設計フェーズ」ごとに分割**し、各チャットの冒頭に「引き継ぎサマリー」を貼る
- **実作業（コマンド実行、ファイル生成）はローカルで行い、結果のみを送る**

## 3. このスレッドで学んだ教訓（PMO設計原則）

今回の失敗から、PMO運用の**5原則**が導けます：

### 原則①：チャットは「短期記憶」と心得る

LLMのコンテキストは**揮発性**。1チャットで扱えるのは**せいぜい数百ノート分**。6,770ノートは物理的に無理。

### 原則②：巨大ファイルは絶対に貼らない

`tree /F` の全体出力、`Box/` 配下の全PDFテキスト、全ノート本文 → **すべて禁止**。
代わりに：
- フォルダ名のみ（47行）
- ノート数集計
- 特定フォルダの中身（1階層）
- 個別ノート1〜2件

### 原則③：永続記憶はVault側に置く

- **Dailynote** に設計判断・ADR・引き継ぎサマリーを記録
- **GitHub** にコード・データを集約
- **ChromaDB** に全ノートをインデックス化
- チャットは**それらを参照するだけ**

### 原則④：フェーズで分割する

```
[PMOスレッド]  → 構造確定・設計判断
     ↓ 引き継ぎサマリー
[実装スレッド] → コマンド実行・コード生成
     ↓ 結果
[PMOスレッド]  → 検証・次の設計
```

1つのスレッドで「構造把握→設計→実装→検証」を全部やると必ず破綻。
