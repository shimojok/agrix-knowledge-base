# 2. JSON Schemaの設計原則

### Principle A — Semantic Separation

```
Taxon
 ≠ Function
 ≠ Functional Capacity
 ≠ Activity
 ≠ Metabolite
 ≠ Clinical Effect
```

### Principle B — Evidence First

重要なRelationshipは原則として、

```
Relationship
    ↓
Claim
    ↓
Evidence
```

を辿れる構造にします。

### Principle C — Unknownを保持

不明な情報を`false`や`0`に変換しません。

```
unknown ≠ absent
```

これはMIOS AI Reasoningで極めて重要です。

ここが今回の最重要Schemaです。

```
{
  "id": "EMF-EQUOL-001",
  "entity_type": "EssentialMicrobialFunction",
  "schema_version": "1.0",
  "function_id": "FUNC-EQUOL-001",
  "essentiality_class": "context_dependent",
  "host_domains": [
    "endocrine"
  ],
  "dependency_type": "microbiome_dependent",
  "redundancy_level": "unknown",
  "evidence_ids": [],
  "status": "draft"
}
```

### `essentiality_class`

```
essential
beneficial
context_dependent
unknown
potentially_harmful
```

**「Essential」という名称を持ちますが、実際の分類値はEvidenceに基づいて慎重に管理します。**

# 15. Claim Schema

Knowledge GraphではRelationshipを単なるedgeにしません。

```
{
  "id": "CLAIM-0001",
  "entity_type": "Claim",
  "subject_id": "PHY-DAIDZEIN-001",
  "predicate": "substrate_for",
  "object_id": "FUNC-EQUOL-001",
  "evidence_ids": [
    "EVID-0001"
  ],
  "confidence": "high",
  "status": "approved"
}
```

これにより、

```
Daidzein
   │
   └── substrate_for
             │
             ▼
       Equol Function
```

というRelationshipそのものにEvidenceを付与できます。

# 17. Relationship Contract

MIOS KG v1.0で許可する主要Relationshipを固定します。

```
CONTAINS
SUBSTRATE_FOR
PERFORMS
CONTRIBUTES_TO
EXPRESSES
ENABLES
PRODUCES
CROSS_FEEDS_WITH
TARGETS
MEDIATES
ASSOCIATED_WITH
SUPPORTS
```

特に、

```
ASSOCIATED_WITH
```

と

```
CAUSES
```

を混同しないようにします。

**v1.0では一般的な`CAUSES`を自由生成可能なRelationshipにはしません。**
