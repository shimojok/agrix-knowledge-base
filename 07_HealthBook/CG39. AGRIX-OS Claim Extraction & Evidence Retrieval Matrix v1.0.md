# 1. 正式目的

### Objective

29 Objectsを、

> **「AIが説明する対象」から「Evidenceによって判定可能なClaim集合」へ変換する。**

そのために各Claimについて以下を固定します。

|項目|内容|
|---|---|
|Object|対象Canonical Object|
|Claim|検証対象となる主張|
|Claim Type|Architecture / Function / Data / Implementation / Evidence等|
|Source Class|Repository / Document / Code / Dataset|
|Retrieval Method|RAG / AST / Exact Search|
|Evidence Requirement|必要Evidence|
|Evidence Status|Found / Missing / Conflict|
|Provenance|Source → File → Chunk/Node|
|Adjudication Requirement|Human判定の必要性|

# 2. Claimの分類体系

v1.0ではClaim Typeを次の6分類に固定します。

```
CLAIM
│
├── C1 Architecture
├── C2 Function
├── C3 Data / Interface
├── C4 Implementation
├── C5 Evidence
└── C6 Dependency / Relationship
```

### C1 Architecture

システム構造、Layer、Module、Component、Data Flow。

### C2 Function

何を実現する機能なのか。

### C3 Data / Interface

入力・出力、Schema、Data Contract、データ連携。

### C4 Implementation

Repository、Python、JSON、API、Dashboard等に実装が存在するか。

### C5 Evidence

実証、文献、実験、Case、観測等に関するClaim。

### C6 Dependency / Relationship

MBT55 → MSC → AGRIX → SafetyChain → PBPE等の関係性。

# 3. Claim Extraction Rule

最も重要なルールです。

## ClaimをAIが新規発明しない

```
Source
  ↓
Existing Statement
  ↓
Atomic Claim
```

です。

したがって、

```
Sourceに存在しない
        ↓
AIが推測
        ↓
新しいClaim
```

は禁止します。

必要な場合は、

```
INFERRED_CLAIM
```

として明示的に別管理します。

---

# 4. Atomic Claim

例えば、

> 「SafetyChainは農産物の品質・機能性・鮮度・トレーサビリティを統合し、PBPE金融データを生成する」

という文章があった場合、

```
CLM-A
SafetyChain manages quality.

CLM-B
SafetyChain manages functionality.

CLM-C
SafetyChain manages freshness.

CLM-D
SafetyChain manages traceability.

CLM-E
SafetyChain generates PBPE-related data.
```

のように分解します。

これにより、一部だけEvidenceが存在する場合でも正確に判定できます。

# 6. RAG Evidence

RAGは主として、

- Architecture documents
- Markdown
- README
- Specifications
- Design documents
- Narrative descriptions

を対象とします。

```
Claim
 ↓

 ↓

 ↓
Top-k Candidates
 ↓

```

### 重要

Top-k結果は**Evidence候補**であって、Evidence確定ではありません。

# 7. AST Evidence

ASTは、

- Python
- JavaScript
- TypeScript

等の構造化コードに適用します。

取得対象：

```
Module
Class
Function
Import
Call
Variable
Dependency
```

例えば、

```
Claim:
"PBPE Dashboard contains KPI calculation logic."

AST:
Dashboard module
 ├── KPI function
 ├── calculation function
 └── data loader
```

のように、**実コード上の構造Evidence**を取得します。

# 8. Source Priority

Evidence Sourceの優先順位を固定します。

```
Priority 1
Canonical Source File
        ↓
Priority 2
Repository Code / JSON / Schema
        ↓
Priority 3
Repository Documentation
        ↓
Priority 4
Validated External Evidence
        ↓
Priority 5
Legacy AI-generated Document
```

ただし、Priorityが低いから無価値という意味ではありません。

**Legacy AI DocumentsもCandidate Evidenceとして検索対象に残します。**

これは今回の方針に合致します。

# 9. Legacy AI Knowledgeの扱い

ここは今回、特に重要です。

過去AIが作成した、

- Architecture
- Implementation description
- Scientific interpretation
- Dashboard explanation
- Repository summary

は**捨てません。**

しかし、

```
Legacy AI Statement
       ↓
Candidate Claim
       ↓
Current Source Retrieval
       ↓
Current Evidence
       ↓
Adjudication
```

という経路に置きます。

つまり、

> **過去AIの成果を「使わない」のではなく、「現在のEvidenceとして再利用可能なCandidate Knowledge」に戻す。**

これが今回の取捨選択です。

# 10. Evidence Status

各ClaimのEvidence状態を以下に統一します。

```
FOUND
PARTIAL
CONFLICT
MISSING
UNVERIFIED
NOT_APPLICABLE
```

### FOUND

十分なSource Evidenceあり。

### PARTIAL

一部のみ確認。

### CONFLICT

Source間で内容が異なる。

### MISSING

該当Evidenceを取得できない。

### UNVERIFIED

情報は存在するが、現在の基準では検証不能。

### NOT_APPLICABLE

そのClaimに該当するEvidence Typeが不要。

---

# 11. Evidence StrengthとRetrieval Scoreの分離

必須ルールとして固定します。

```
RAG Retrieval Score
        ≠
Evidence Strength
        ≠
Claim Truth
```

例えば、

```
retrieval_score = 0.94
```

だから、

```
claim_confidence = 94%
```

とはしません。

これは今回のRAG設計における重要な誤用防止策です。
